Dossier technique
Application Cantine

Architecture, déploiement et exploitation — à l'attention de l'équipe IT / DevOps

Version du 5 novembre 2026 · code : github.com/ahmeds1001/app-canteen (branche main)
État : application développée et testée (148 tests automatiques, aussi sur SQL Server 2022), pas encore déployée.
Documents liés : cahier des charges (docs/cahier-des-charges.pdf), guide de test (docs/guide-test-semaine.pdf).

En une phrase

Une application web (site installable sur le téléphone) où ~200 employés réservent leur repas la veille ; la cuisine prépare réservations + 10 % ; un téléphone de la cantine scanne un QR code par repas. Elle tourne dans trois conteneurs Docker (site, API, tâches planifiées) derrière le proxy HTTPS de l'entreprise, avec sa propre base SQL Server, isolée de l'ERP.

1. Synthèse pour l'IT

Ce que l'application demande

  • Un serveur Linux avec Docker + Docker Compose (Windows Server seulement s'il fait tourner des conteneurs Linux) ; 4 vCPU, 4 Go de RAM, 20 Go de disque — estimation avec marge pour un lancement où tout le monde se connecte en même temps, à confirmer par le test de charge (§9.1).
  • Une base SQL Server 2019+ dédiée (canteen) et un login SQL qui n'a des droits que sur elle.
  • Un sous-domaine (ex. cantine.ovagri.tn) avec certificat HTTPS sur le proxy de l'entreprise.
  • Un compte SMTP pour 5 emails de compte (code, validation, refus, mot de passe).
  • Un accès Internet sortant en 443 vers les services push (Google, Mozilla, Apple, Microsoft).
  • Une horloge serveur juste (NTP) : les délais de réservation se jouent à la minute.

Ce que nous attendons de vous

  1. Choix du serveur et de son OS ; Docker autorisé ou non.
  2. Le sous-domaine et qui gère le certificat.
  3. Création de la base et du login SQL (script en §8.2).
  4. Identifiants SMTP et adresse d'expéditeur.
  5. Ouverture des flux réseau du §7.3, et un proxy qui transmet X-Forwarded-For (§7.2).
  6. Sauvegardes : outil et emplacement hors du serveur ; un test de restauration avant le lancement.
  7. Supervision : qui reçoit l'alerte si le site ou les tâches planifiées s'arrêtent.

4. Fonctionnement

4.1 Sessions et API

  • Connexion par email + mot de passe → jeton d'accès JWT valable 30 minutes et jeton de renouvellement de 14 jours, chacun utilisable une fois (rotation + liste noire). Un compte suspendu n'obtient plus de jeton, même sur un téléphone déjà connecté. Les jetons sont gardés par le navigateur (localStorage) ; pas de cookie de session pour l'API.
  • Toutes les routes sont sous /api/v1/ ; chaque route vérifie le rôle côté serveur (l'écran ne fait que masquer).
  • Limitation des tentatives par adresse de l'utilisateur : connexion 10/min, inscription 5/h, codes 20/h, mot de passe oublié 3/h. Les compteurs sont partagés par tous les workers (table de cache dans la base).

4.2 QR code et scan

Chaque réservation porte un jeton aléatoire signé (clé CANTEEN_SIGNING_KEY), sans donnée personnelle. Le téléphone de la cantine lit le QR avec sa caméra (le navigateur exige HTTPS pour la caméra) et l'API passe la réservation à « Servi » par une mise à jour conditionnelle : deux scans simultanés ne peuvent pas réussir tous les deux.

4.3 Tâches planifiées (conteneur scheduler)

Une boucle exécute ces tâches chaque minute. Chacune est idempotente : la relancer ou la lancer en retard donne le même résultat (après une coupure, le premier passage rattrape tout).

TâcheEffet
publish_placeholdersPublie « Menu à venir » si le chef n'a pas publié à temps
lock_menusClôture les réservations à l'heure limite (23:59 la veille par défaut)
finalization_reminder, menu_missing_reminder, evening_reservation_reminderRappels (Direction, chef, employés) aux heures des paramètres
auto_finalizeFixe le nombre d'assiettes (réservations + marge) si la Direction ne l'a pas fait à 10:00
mark_no_shows, close_finished_daysAbsences et fin de journée après le service
send_pending_pushesEnvoie les notifications aux téléphones (timeout 10 s, durée de vie 24 h ; un abonnement mort est retiré)
Une seule instance du conteneur scheduler. Les tâches sont protégées contre les doublons, mais deux planificateurs enverraient deux fois plus de requêtes pour rien. Ne pas le mettre à l'échelle.

4.4 Emails et notifications

  • Email (SMTP) seulement pour le compte : code d'inscription, compte validé ou refusé, mot de passe oublié ou changé. Envoyés après l'enregistrement en base, pour qu'un SMTP lent ne bloque rien.
  • Notifications dans l'application et sur le téléphone (standard Web Push, clés VAPID) : rappels, menu modifié, solde rechargé… Le serveur appelle le service push du navigateur (Google FCM pour Chrome/Android, Mozilla, Apple, Microsoft) en HTTPS sortant ; sans clés VAPID, les notifications restent visibles dans l'application.

5. Données

  • Base : SQL Server, base dédiée canteen, accès par le pilote ODBC Driver 18. 13 tables métier (utilisateurs, plats, menus et leurs plats, réservations, mouvements de solde, notifications et abonnements push, codes email, liens de réinitialisation, paramètres, journal d'audit) + les tables Django.
  • Schéma : créé et modifié uniquement par les migrations Django (python manage.py migrate), jamais à la main. Les migrations sont ajoutées par le développeur et appliquées à chaque mise à jour.
  • Rien n'est supprimé (décision de l'entreprise) : pas de suppression d'utilisateurs, de réservations ni de lignes d'audit ; la suppression est bloquée dans l'administration. Le journal d'audit est en ajout seulement.
  • Fichiers : les photos des plats (media/dishes/, réduites à 1200 px), dans le volume Docker media : elles survivent aux mises à jour et sont sauvegardées avec la base (voir §9).
  • Dates : stockées en UTC ; toutes les règles et l'affichage utilisent Africa/Tunis.
  • Données personnelles : nom, email professionnel, matricule, département, repas, solde. Exports CSV tracés. Loi organique n° 2004-63 : une vérification rapide avec la RH / le juridique est recommandée.

Tous les services redémarrent seuls (restart: unless-stopped) et leurs journaux tournent (10 Mo × 5 fichiers).

7.2 Ce que le proxy HTTPS doit faire

  • Terminer TLS pour cantine.<domaine> et relayer vers http://<serveur>:8080.
  • Transmettre les en-têtes Host et X-Forwarded-Proto: https (indispensable : Django s'en sert pour savoir que la requête était en HTTPS ; le conteneur web le transmet tel quel).
  • Ajouter l'adresse de l'utilisateur dans X-Forwarded-For (indispensable aussi) : la limite de 10 connexions par minute compte par adresse. Sans cet en-tête, tous les employés auraient la même adresse et seules 10 personnes par minute pourraient se connecter dans toute l'entreprise. Si un autre proxy s'ajoute devant, augmenter NUM_PROXIES.
  • Taille de requête ≥ 6 Mo (photos des plats jusqu'à 5 Mo). Pas de cache sur /api/.

8. Installation et mises à jour

8.1 Première installation

git clone https://github.com/ahmeds1001/app-canteen.git cantine && cd cantine
cp .env.example .env            # puis remplir les valeurs du §7.4
docker compose up -d --build    # construit, applique les migrations, démarre
docker compose run --rm backend python manage.py createsuperuser   # le premier compte admin

8.2 Base de données (à faire par l'administrateur SQL Server)

CREATE DATABASE canteen COLLATE French_CI_AS;
CREATE LOGIN canteen_app WITH PASSWORD = '<mot de passe fort>';
USE canteen;
CREATE USER canteen_app FOR LOGIN canteen_app;
ALTER ROLE db_owner ADD MEMBER canteen_app;   -- sur cette base seulement (les migrations créent les tables)

8.3 Clés des notifications push (une fois)

docker compose run --rm backend python manage.py generate_vapid_keys   # 2 lignes à copier dans .env
docker compose up -d                                                  # pour les prendre en compte

8.4 Mise à jour

git pull
docker compose up -d --build    # les migrations passent avant le redémarrage de l'API

Moins d'une minute d'interruption ; à faire hors des pics (pas entre 23:30 et 00:15, ni entre 11:45 et 15:00). Les tâches planifiées rattrapent seules ce qui est tombé pendant la coupure.

8.5 Vérifications après installation

  • https://cantine.<domaine>/api/v1/health/ répond {"status": "ok", "database": "ok", "server_time": …} avec l'heure de Tunis ; docker compose ps montre le backend « healthy ».
  • docker compose logs scheduler montre une ligne « Scheduler tick » par minute, sans -1 (tâche en échec).
  • Inscription d'un compte de test : l'email avec le code arrive.
  • Sur un téléphone : « Activer » les notifications, recharger un solde, la notification arrive.
  • /admin/ s'affiche avec sa mise en forme ; une photo de plat ajoutée par le chef s'affiche sur l'accueil.

9.1 Test de charge (avant le lancement)

Le kit est dans le dépôt : loadtest/ (mode d'emploi loadtest/README.md). Il se lance sur une installation de test à côté de la vraie, avec sa propre base canteen_loadtest : les 200 comptes de test ne doivent jamais entrer dans la base réelle (rien n'y est supprimé). La commande loadtest_accounts crée les comptes avec 100 TND et ouvre un jour à deux menus ; elle refuse de tourner sur une base dont le nom ne contient pas « loadtest ».

ScénarioCe qu'il simuleRéussi si (95 % des requêtes)
LoginRushJour du lancement : 200 comptes se connectent une fois, dans la même minuteconnexion < 5 s, moins de 1 % d'erreurs
ReservationRushRush du soir : 200 personnes pendant 5 min (menus, réserver, changer de menu, annuler, solde)< 1 s (connexion < 5 s), moins de 1 % d'erreurs

Essai à blanc sur le poste de développement (serveur de développement, un seul processus) : 60 connexions simultanées et 1 027 requêtes de rush, aucune erreur, 95 % des réservations en moins de 63 ms. Il valide le kit ; le vrai chiffre viendra du serveur. La connexion est volontairement la requête la plus lourde (vérification Argon2 du mot de passe, ~100 Mo) : c'est elle qui dimensionne le CPU et la mémoire du backend.
